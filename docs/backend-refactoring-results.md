# Рефакторинг заказов и бронирований — результат

15 октября 2026 года. Выполнен рефакторинг центрального сценария заказа:
`dinein`, создание/подтверждение предзаказа, чтение клиентских броней и смена
статуса заказа в Vendor. API и сериализация входных запросов сохранены.

## Изменения кода

- В `dinein` разделены модели, интерфейсы, сервис QR, выдача QR,
  создание заказа, чтение чека и история. `Create` явно управляет одной
  транзакцией и вызывает именованные шаги повторной отправки, проверки корзины,
  открытия счёта и записи результата.
- В `reservations` модели и интерфейсы отделены от сервиса. Прямое создание
  и подтверждение hold используют общий `pricePreorder` и `insertPreorder`.
- `orderstore` содержит общие SQL-операции с меню, снимками позиций и pending-
  чаевыми. Бизнес-операция с чаевыми перенесена из инфраструктурного `database`.
  Общий адаптер принимает транзакцию вызывающей стороны и не делает commit.
- Меню читается одним запросом с блокировками `FOR SHARE`, позиции записываются
  одним `INSERT` с массивами. Соответствие ID/названия/цены/количества сохраняется
  независимо от порядка строк, возвращённого PostgreSQL.
- Чек и история используют одну проекцию и один сканер. Lookup проверяет право
  доступа в самом запросе чека, убирая отдельное чтение авторизации.
- Сводка брони и поиск по idempotency key читают первый предзаказ одним LATERAL
  вместо нескольких одинаковых подзапросов. Выбор при одинаковом времени
  теперь однозначен по `(created_at, id)`.
- Загрузка позиций брони использует UUID без преобразования индексируемой
  колонки в text. Vendor загружает позиции именно уже выбранных 200 заказов:
  повторный выбор последней страницы между двумя запросами больше не происходит.
- Смена статуса разделена на захват блокировок/проверки, обновление и однократную
  корректировку счёта/чаевых при отмене. Правила статусов сохранены.
- Архитектурный тест запрещает импорт `orderstore` сервисами модулей, как и pgx.

## Схема данных

Добавлена обратимая миграция **000018_preorder_lookup_index**:

```sql
CREATE INDEX orders_reservation_preorder_idx
  ON orders (reservation_id, created_at, id)
  WHERE channel = 'preorder' AND reservation_id IS NOT NULL;
```

Этот путь ранее не имел индекса по reservation_id. Индекс обслуживает сводку,
поиск результата подтверждения и выборку связанных заказов при отмене.
Перестройка таблиц, удаление данных и backfill не нужны. Существующие снимки
и JSON-план помещения сохраняются: их перенос потребовал бы самостоятельной
миграции всех читающих/пишущих компонентов.

Миграция применена и отменена в изолированной тестовой схеме. На рабочей
локальной БД в рамках этого изменения не запускалась; приложение пока использует
прежний Docker-образ. При обновлении backend нужно применить миграцию штатным
мигратором. Обычный CREATE INDEX может блокировать записи во время построения;
для большой рабочей базы следует планировать окно либо отдельное создание
CONCURRENTLY вне транзакции мигратора.

## Измерения

Среда: локальный Docker, Go 1.23, PostgreSQL 17 в tmpfs. Исходный код снят
до рефакторинга, включая ранее существовавшие изменения рабочего дерева.
Одинаковый интеграционный тест выполнен трижды на исходной и новой версии.
Время ниже — медиана трёх прогонов, без подготовки данных и проверки результата.
Это локальный профиль, а не нагрузочный тест или прогноз production p95.

| Разных блюд | SQL-вызовов до | После | Время до | После |
| --- | ---: | ---: | ---: | ---: |
| 1 | 14 | 14 | 6,69 мс | 6,77 мс |
| 10 | 32 | 14 | 4,06 мс | 2,53 мс |
| 100 | 212 | 14 | 19,24 мс | 3,84 мс |

Число вызовов измерено pgx QueryTracer, включая BEGIN/COMMIT, создание заказа
и чаевые 5%. Случай с одним блюдом первым открывает счёт и подготавливает
SQL-запросы соединения; поэтому он может быть медленнее последующих корзин.
Для 100 блюд уменьшение числа вызовов — около 93%, времени — около 80%.
Тест ограничивает бюджет 20 вызовами, чтобы обнаружить возвращение запросов
в цикле; время выполнения не является условием прохождения теста.

Отдельный EXPLAIN (ANALYZE, BUFFERS) на настоящей мигрированной схеме:
1000 броней × 50 предзаказов, всего 50 000 заказов. Измеряется получение
первого предзаказа по reservation_id, не весь HTTP-ответ списка броней.

| План | Затронуто shared blocks | Медиана выполнения |
| --- | ---: | ---: |
| Без индекса, Seq Scan | 962 | 2,209 мс |
| С индексом, Index Scan | 4 | 0,023 мс |

Индекс проверен без принудительного отключения Seq Scan. Тест применяет down,
измеряет исходный план, применяет up и подтверждает использование индекса.

## Проверки и воспроизведение

Пройдены `go test -count=1 -v ./...` с PostgreSQL и `go vet ./...`.
91 тест верхнего уровня, 174 с учётом под-тестов; пропущенных тестов нет.
Проверены архитектурные ограничения, HTTP-контракты, QR, изоляция истории,
конкурентные повторы, чаевые, бронирование, hold, отмена и новые сценарии:

- корзины 1/10/100 блюд, смешанные количества, UUID в верхнем регистре;
- соответствие снимков ID, названиям, количеству и цене;
- повтор после смены цены, отсутствие частичной записи при ошибке;
- откат заказа, позиций и чаевых при переполнении счёта;
- реальные блокировки изменения цены и категории;
- пакетные снимки в прямом предзаказе и подтверждении hold;
- up/down миграции индекса и его план исполнения.

Полная проверка одной командой из каталога backend:

```sh
./scripts/test-integration.sh -count=1 -v ./...
```

Скрипт создаёт отдельную PostgreSQL в tmpfs, без опубликованного порта и
рабочих томов, использует Go 1.23 в контейнере, затем удаляет PostgreSQL.
Именованные кеши компилятора и модулей Go переиспользуются. Нужен Docker.
Это также устраняет риск случайного пропуска интеграционных тестов при пустом
TEST_DATABASE_URL. Настройки удалённого CI этим изменением не добавлялись.

Повторить профиль:

```sh
./scripts/test-integration.sh -run 'TestTableOrderBatchIntegration|TestPreorderLookupIndexIntegration' -count=3 -v ./internal/bootstrap
```

На компьютере с Go 1.23 дополнительно: `go vet ./...`. Интеграции также можно
запустить обычным go test, передав TEST_DATABASE_URL на отдельную БД с именем,
заканчивающимся `_test`; каждый тест создаёт и удаляет собственную схему.

## Документация и границы

[Бизнес-правила](order-business-rules.md) описывают источники истины,
транзакции, доступ, совместимость повторной отправки, суммы, отмену и
ограничения будущей оплаты. [Архитектура](architecture.md) обновлена по коду.

Рефакторинг не вводит новую матрицу переходов статусов, платёжного провайдера
или микросервисы. Публичный поиск заведений, отчётность и identity остаются
за пределами этого изменения: для их оптимизации нужны отдельные профили.
