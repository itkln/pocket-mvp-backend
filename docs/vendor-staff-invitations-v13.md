# V-13 — приглашения сотрудников

## Поведение

1. Владелец открывает Команда → Пригласить сотрудника, вводит имя, e-mail и роль.
2. Создаётся invited membership без user_id. На e-mail отправляется ссылка.
3. Сотрудник входит или регистрируется с этим e-mail. Ссылка сохраняется при переходе между входом и регистрацией.
4. После входа он видит заведение и назначенную роль, нажимает «Принять приглашение».
5. Сервер атомарно привязывает аккаунт и активирует membership. Кухня открывается на /ru/staff/kitchen, остальные роли — /ru/staff/service. Выбирается приглашённое заведение.
6. Владелец может менять роль, приостанавливать и удалять доступ. Сервер проверяет membership на каждом операционном запросе.

Владение заведением не выдаётся через приглашение. Уже существующие права владельца другого заведения сохраняются.

Ссылка одноразовая, срок — 72 часа. В БД только SHA-256 токена; исходный токен отправляется в письме.
Повторная отправка разрешена раз в минуту и заменяет предыдущую ссылку.
Удалённые/неактивные/принятые приглашения недействительны. При ошибке SMTP приглашённая запись остаётся,
но токен удаляется; интерфейс сообщает об ошибке и предлагает повторить отправку через меню команды.
Роль берётся из membership на момент принятия, а не из данных клиента.
Перед принятием блокируются строки аккаунта и membership; проверяется актуальный e-mail.
Непринятое приглашение нельзя вручную перевести в active через PATCH.

## Настройка окружения

Применить миграцию 000022_staff_invitations.up.sql перед обновлением backend.
Письма используют существующие SMTP_ADDRESS, SMTP_USERNAME, SMTP_PASSWORD, SMTP_FROM.
Ссылка строится из настроенного Vendor APP_BASE_URL, а не из HTTP Host.
В production конфигурация приложения требует SMTP_ADDRESS.

Без SMTP в development внешнее письмо не отправляется: ссылка записывается в локальный лог backend
с сообщением «staff invitation captured by development sender». Это режим локальной проверки.
Не используйте реальные адреса для автоматических тестов.

## Ручная проверка

1. Под владельцем открыть http://localhost:3000/ru/owner/team.
2. Пригласить отдельный тестовый e-mail с ролью «Кухня». Убедиться в статусе «Приглашен».
3. Открыть ссылку из письма в другом профиле браузера. Без SMTP взять ссылку из локального лога.
4. Нажать «Создать аккаунт» или «Войти», используя адрес приглашения.
   После успешной авторизации должна снова открыться страница приглашения.
5. Нажать «Принять приглашение»: откроется кухня нужного заведения. В меню владельца запись станет активной после обновления.
6. Проверить реальные заказы: кухня может начать приготовление и отметить готовность, но не получает права владельца и финансовые данные.
7. Открыть ссылку повторно: принятие недоступно.
8. Создать другое приглашение и попробовать принять под чужим e-mail: отказ и предложение сменить аккаунт.
9. Отправить приглашение снова через «…» в команде. Старая ссылка не работает, новая работает. Повтор ранее минуты отклоняется.
10. Удалить ещё не принятое приглашение: его ссылка не работает.
11. Удалить принятого сотрудника: его текущая сессия больше не получает заказы заведения.
12. Повторить для официанта, менеджера и наблюдателя. Проверить переход в сервис и разрешённые действия.
13. При недоступном SMTP запись остаётся приглашённой, интерфейс показывает ошибку доставки. После восстановления SMTP повторить отправку.

## Проверка автоматически

Из frontend:

    npm test -- shared/staff-invitation-page.test.tsx shared/auth-page.test.tsx features/pocket/staff/workspace.test.tsx
    npm run build:vendor

Из backend, отдельная pocket_test БД:

    GOROOT=/opt/homebrew/opt/go/libexec TEST_DATABASE_URL='postgres://pocket:pocket_local_password@localhost:5432/pocket_test?sslmode=disable' go test ./...
    GOROOT=/opt/homebrew/opt/go/libexec TEST_DATABASE_URL='postgres://pocket:pocket_local_password@localhost:5432/pocket_test?sslmode=disable' go test -race ./internal/bootstrap -run TestStaffInvitationIntegration -count=1

HTTP-интеграционный тест использует изолированную схему и локальный SMTP-приёмник.
Покрыты доставка, хэш и срок токена, чужой e-mail, отсутствие доступа до принятия,
ограничение повторной отправки, аннулирование старой ссылки, гонка принятия,
сохранение назначенной роли, отсутствие owner capability, отзыв доступа и ошибка SMTP.
Frontend-тесты проверяют сохранение приглашения в auth-ссылках, явное подтверждение,
блокировку повторного клика, назначенное заведение, ошибки и защиту от внешнего returnTo.
