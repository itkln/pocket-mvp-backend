# V-ORD-05 — проверка кухни и сервиса

## Реализация

Кухня и сервис используют общую серверную очередь и карточку заказа.
GET /api/v1/staff/venues возвращает только заведения владельца или активного,
не удалённого сотрудника с привязкой venue_staff.user_id к текущему аккаунту.
Приватные настройки заведения не выдаются.
Запросы заказов идут через /api/v1/venues/{venueID}/orders.
Staff workspace не запрашивает dashboard, платежи, меню и команду владельца.

Основная кнопка соответствует статусу и allowed_actions из API.
Если allowed_actions отсутствует или пуст, действий нет. Отмена тоже требует
разрешения сервера. PATCH передаёт expected_status, сохраняет ответ сервера,
блокирует повторный клик; ошибка не считается успехом и запускает обновление очереди.
Автообновление — каждые 15 секунд на видимой вкладке.

| Аккаунт | Доступные переходы |
|---|---|
| Владелец / manager | Принять → Начать приготовление → Заказ готов → Заказ подан → Завершить |
| waiter | Новый → Принят; Готов → Подан |
| kitchen | Принят → Готовится; Готовится → Готов |
| viewer | Только просмотр |

Отмена доступна владельцу/менеджеру с учётом серверных ограничений счёта.
Готовность, подача и завершение заказа не оплачивают и не закрывают счёт.
Кухонный JSON не содержит цен, итогов, чаевых и персональных данных гостя.

## Быстрая проверка владельцем

1. Войти в http://localhost:3000/ru/login владельцем.
2. Открыть /ru/staff/service, выбрать заведение. Номера и блюда совпадают
   с /ru/owner/orders. Нет фиктивной смены, сотрудника и часов.
3. Открыть /ru/staff/kitchen. Под владельцем сохраняются права владельца:
   это проверка интерфейса, НЕ проверка ограничений роли kitchen.
4. Создать тестовый QR-заказ через Dish, открыть его в очереди.
5. Пройти действия; после каждого перезагрузить страницу.
   Статус сохраняется, следующая кнопка изменяется.
6. На телефоне открыть заказ: блоки на всю ширину, одно действие свайпом.
   Простое нажатие не подтверждает свайп. Enter/Space подтверждают с клавиатуры.
   Отмена находится возле возврата к очереди.
7. После завершения заказ находится в «Истории», а не в активных.

## Подготовка аккаунтов для проверки ролей

Нужны отдельные аккаунты manager, waiter, kitchen, viewer с АКТИВНОЙ привязкой
к одному заведению. Не используйте владельца для проверки скрытия финансов:
сервер отдаёт ему права владельца независимо от экрана.

Приглашение и принятие реализованы в V-13. Подготовьте сотрудников через
«Команда → Пригласить сотрудника», откройте письмо и примите приглашение
под соответствующим аккаунтом. Ручная привязка user_id больше не требуется.
Инструкция и локальная настройка SMTP: [V-13](vendor-staff-invitations-v13.md).

## Полная проверка по ролям

Открыть разные профили браузера/приватные окна, чтобы сессии не заменяли друг друга.

1. **waiter:** /ru/staff/service. Новый QR-заказ → «Принять заказ».
   После успеха нет кнопок приготовления и отмены.
2. **kitchen:** /ru/staff/kitchen. Тот же заказ → «Начать приготовление» →
   «Заказ готов». Видны состав, количество, комментарии, стол/время визита.
   Не видны цена, сумма, чаевые, имя и телефон гостя. Проверить JSON ответа
   orders в Network: данные отсутствуют и там.
3. **waiter:** дождаться обновления или нажать «Обновить» → «Заказ подан».
   Нет кнопки завершения и финансовых операций.
4. **manager:** /ru/staff/service → «Завершить заказ».
   Счёт остаётся в прежнем состоянии, платёж не появляется.
5. **viewer:** заказ виден, кнопок смены статуса и отмены нет.
6. Повторить для предзаказа: время визита сохраняется; кухня не видит контактов.
7. Сотрудник двух заведений может переключаться между ними.
   Очередь и выбранный заказ сбрасываются при смене заведения.
8. Отключить сотрудника через команду владельца: новые запросы и изменения
   недоступны; после перезагрузки заведение исчезает из списка.
   Старый экран может показывать последние данные с ошибкой обновления,
   но сервер не разрешает новые действия.

## Ошибки и конкурентные действия

- DevTools → Offline, выполнить действие. Появляется ошибка,
  статус не изменяется локально. Вернуть Online, обновить и повторить.
- Slow 3G, дважды нажать действие: в Network один PATCH,
  кнопка заблокирована до ответа.
- Открыть заказ в двух сессиях. Первая меняет статус; вторая до обновления
  выполняет несовместимое действие со старым expected_status.
  API возвращает 409, UI обновляет фактический статус и показывает ошибку.
  Повтор уже выполненного того же перехода идемпотентен и может вернуть 200.
- Для конфликта: первый менеджер принимает новый заказ, второй со старым
  состоянием пытается отменить его. Ожидаемый new, фактический accepted → 409.
- «Готов»/«Подан»/«Завершён» не создают платежи и не меняют суммы/статус bills.

## Автоматическая проверка

Из frontend:

    npm test -- features/pocket/staff/workspace.test.tsx features/pocket/owner/orders.test.tsx lib/owner-orders-api.test.ts
    npm run build:vendor

Из backend с отдельной pocket_test БД:

    GOROOT=/opt/homebrew/opt/go/libexec TEST_DATABASE_URL='postgres://pocket:pocket_local_password@localhost:5432/pocket_test?sslmode=disable' go test ./...
    GOROOT=/opt/homebrew/opt/go/libexec TEST_DATABASE_URL='postgres://pocket:pocket_local_password@localhost:5432/pocket_test?sslmode=disable' go test -race ./internal/bootstrap -run 'TestOrder(Policy|Queue)Integration' -count=1

Тесты используют изолированные схемы. Проверяются роли, удалённые/неактивные
привязки, отсутствие финансов в кухонном JSON, конфликты, идемпотентность
и неизменность счёта при готовности, подаче и завершении.
