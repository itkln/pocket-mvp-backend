# V-ORD-01: состояния заказа и права

Доступ определяется владельцем или активной записью venue_staff с user_id. Приглашённый, удалённый и неактивный сотрудник доступа не имеет. Права других модулей не расширяются.

| Роль | Действия |
| --- | --- |
| owner, manager | Чтение, допустимые переходы, отмена |
| waiter | Чтение, new → accepted, ready → served |
| kitchen | Чтение без персональных/финансовых полей, accepted → preparing, preparing → ready |
| viewer | Только чтение |

Для dine_in, preorder и существующего online: new → accepted → preparing → ready → served → completed. Для pickup: ready → completed (передача вместо подачи, owner/manager). Отмена доступна owner/manager до completed; финальные состояния нельзя возобновить. Готовность, подача и завершение не создают платёж и не закрывают счёт.

PATCH /api/v1/owner/venues/{venueID}/orders/{orderID} сохраняет прежний маршрут с доступом по роли. JSON содержит обязательные status и expected_status, например {"status":"preparing","expected_status":"accepted"}. expected_status — монотонный токен конкурентности: переходов назад нет. Несовпадение исходного состояния или недопустимый переход даёт 409 с error.code=order_status_conflict и current_status. Запрещённое действие роли — 403; чужое заведение/отсутствующее членство — 404. Повтор текущего целевого статуса возвращает успех без UPDATE, изменения timestamps и финансовых эффектов. Повтор после дальнейшего продвижения — 409.

Транзакция повторно проверяет роль и блокирует заведение/членство FOR SHARE, затем заказ FOR UPDATE и счёт FOR UPDATE. Сохраняется порядок order → bill отмены брони. SQL запрещает изменение заказа отменённой брони. Отмена сохраняет проверки платежей, оплаченных чаевых и закрытого счёта; суммы корректируются только при первой отмене.

Ответ кухни: ID, номер, канал, источник/стол, статус, время, время визита, комментарий, названия и количества блюд. Имя/телефон, суммы, цены, валюта, чаевые и код брони не сериализуются. Свободный комментарий гостя остаётся видимым для приготовления.

Существующий клиент владельца отправляет expected_status. Backend и клиент развёртываются вместе: старый PATCH без поля получает 422. Подключение staff-экранов — V-ORD-05, пагинация и расширенный API — V-ORD-02.

Проверки: policy_test.go (матрица ролей/статусов, stale/replay, JSON кухни), order_policy_integration_test.go (PostgreSQL, членства, гонки, replay timestamps), существующие gratuity, reservation cancellation/preorder и table orders. Интеграционные тесты используют отдельные схемы базы с суффиксом _test.
