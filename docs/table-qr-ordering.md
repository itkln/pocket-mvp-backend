# E-16: table QR ordering

Scanning a table code opens `/{locale}/qr/{token}` in Spots. This reuses the
published venue page, information panel, category navigation and dish details
(including images and nutrition), with a table cart instead of reservation
controls. Non-QR venue pages retain the reservation/preorder flow. Table orders
use all available published categories, independently of preorder settings.

## Codes in Vendor

Save the floor plan, then open its QR codes or download the selected table's
code. Codes are generated by the backend, rendered as actual QR images and can
be downloaded as printable SVGs. Downloading again preserves the printed code.
Regenerating a code immediately revokes the preceding code. Removed, disabled,
or unpublished tables/venues cannot resolve. Configure `SPOTS_APP_BASE_URL` to
the public Spots origin; on local development LAN, Vendor replaces a localhost
hostname with the current hostname so a phone can reach Spots on port 3001.

Migration `000015_table_qr` stores a unique SHA-256 token hash and an AES-GCM
encrypted copy for owner re-download. Tokens contain 256 random bits, are never
accepted as a table ID, and are not exposed in ordinary public venue responses.

## HTTP contracts

All responses use `Cache-Control: no-store`. Tokens are sent in JSON bodies.

- POST `/api/v1/venues/{venueID}/table-qr` (владелец и менеджер):
  `{ "table_identifier": "07", "rotate": false }` → `{ "qr": { "url": "…", … } }`.
  Requires ownership of the venue. Normalizes the selected saved floor-plan table.
- Public POST `/api/v1/public/table-qr/resolve`: `{ "token": "…" }` →
  `{ "table": { "venue_id": "…", "table_id": "…", "table_identifier": "07",
  "version": 1, "currency": "EUR", "ordering_enabled": true } }`.
- Public POST `/api/v1/public/table-orders`: token, idempotency_key (16–128
  characters), notes (up to 2000 bytes), items with menu_item_id, quantity (1–30)
  and expected_price_minor. Returns the created order and item snapshots.
  An authenticated session may attach its customer; guests can order without
  registration. Prices, currency, publication and availability are checked by
  the server. Changed prices require renewed guest confirmation.
- Public POST `/api/v1/public/table-orders/lookup`: token + idempotency_key →
  only that order's receipt/status. Neither resolve nor lookup discloses bill
  contents, other guests' orders or contact information.

Errors: `qr_invalid` (404), `price_changed`, `item_unavailable`, `bill_locked`,
`conflict` (409), `invalid_input` (422), `not_found` (404).

## Order and bill lifecycle

The dinein adapter locks the resolved table, checks idempotency, snapshots the
selected menu and creates the order in a single transaction. It attaches to the
current open bill, or opens one when none exists. A bill being paid, or having an
active payment, rejects additions. Paid bills are never reused. Reusing a key
with changed input/table/account is rejected; retries return the original order
without increasing the bill again. Vendor receives the order through its
existing orders API with source `Стол 07` and item snapshots.

Spots keeps a cart and its pending request key in session storage per QR code.
It restores the guest's own receipt after reload and refreshes status every ten
seconds while visible. Mobile uses a dedicated cart dialog and the existing
blue bottom action style. Payment is at the venue; this feature does not charge
cards.

## Verification

`TestTableQRIntegration` uses an isolated PostgreSQL database to cover issuing,
stable download, rotation/revocation, owner isolation, current/new bill linking,
concurrent retries, snapshots and Vendor statuses, price/foreign-item validation,
payment lock and receipt privacy. Frontend tests exercise the real venue menu,
cart, retries, HTTP phone support, price refresh, per-table restoration and owner
QR regeneration. Both Spots and Vendor production builds are required.

## E-29: venue history and repeat orders

Migration `000016_venue_order_history` adds a hashed guest capability, the table
identifier snapshot and QR version to dine-in orders. Account history is keyed
by venue/customer; anonymous history by venue/guest hash. The random 256-bit
`pocket_table_guest` HttpOnly cookie lasts a year, uses SameSite=Lax and the
configured Secure policy, and is established when a valid QR resolves. Clearing
cookies removes anonymous history access on that device. The database never
stores the raw capability. An authenticated session takes precedence and cannot
read a different account or device's orders.

POST `/api/v1/public/table-orders/history` takes `{venue_id, legacy_keys?, cursor?}`.
It returns `{orders, scope, scope_key, next_cursor?}` with no-store caching and
30 orders per page (created_at/id keyset cursor). scope_key is a non-secret cache
identifier, not an access credential. Neither a QR nor a client-supplied user ID
selects the owner. Invalid sessions fail closed. Orders include original table,
items, modifiers, prices, total and status; menu changes never rewrite receipts.

For migration the frontend collects existing secret receipt keys from all QR
carts in sessionStorage. The server only claims unowned legacy dine-in orders
belonging to the requested venue, never orders already owned by an account or
another device. Batches are deduplicated; revoked QR tokens are not required.
Old unclaimed receipt lookup remains capability-based; claimed receipts require
the matching account/device even when a caller knows the receipt key.

Repeat checks the current QR and reloads the published menu, matches stable item
IDs, and previews current prices/currency plus skipped unavailable positions.
The MVP has no selectable modifier catalog: old modified positions are explicitly
skipped and require reselection rather than silently dropping options. Quantities
are capped at 30; a nonempty cart offers merge or replacement. Applying a repeat
only edits the current QR cart. The existing explicit send/idempotency flow links
the new order to the current table and current bill; there is no automatic send.

`TestVenueOrderHistoryIntegration` verifies device/account/venue isolation,
legacy import after QR rotation, persistent cookie privacy, unchanged snapshots,
current table/bill linking and pagination with equal timestamps. Frontend tests
cover repeat review, price changes, missing items/options, merge/replace, delayed
cancellation and pagination refresh. Mobile and desktop use the same history
receipt and review flow.
